# Рольово-доступова модель D.Church CRM

**Статус:** модель узгоджена й реалізована. Роль `PASTOR`, обліковий шар і звуження прав
адміністратора — на погодженні, у гілці `feature/pastor-role`.

## Навіщо це записано

CRM тримає персональні дані людей церкви — не просто контакти, а пасторські нотатки:
з ким про що говорили, хто в якому стані, хто зірвався. Це не той обсяг, який тримають
у голові або узгоджують усно. Тому тут описано, **хто що може робити** і **кого при цьому
бачить**, з причинами — щоб через рік новий лідер або новий розробник не вгадував.

## Чотири принципи

1. **Роль — це дії. Область — це люди.** Роль каже, що людина взагалі вміє робити в системі
   (вести картки, асайнити, керувати довідниками). Область каже, до кого ці дії застосовуються.
   Це два різні виміри; якщо їх змішати, через півроку буде двадцять ролей на кшталт
   «лідер домашньої групи, який ще й помічник у прославленні».
2. **Участь і опіка — різні звʼязки.** Те, що людина в твоїй команді, не робить тебе
   відповідальним за її душу. Чутливе висить на опіці, а не на структурі. Це ключ до всього
   документа.
3. **Лідер працює з тими, кого йому довірили.** Інструмент дається лідеру, щоб він стежив
   за своєю командою: у кого скільки служінь, хто як відвідує, кому потрібна увага.
   Не для того, щоб добирати собі нових людей.
4. **За замовчуванням — не видно.** Кожне розширення доступу має бути свідомим рішенням,
   а не побічним ефектом того, що людина десь лідер.

## Два звʼязки з людиною

|                  | Участь                                       | Опіка                        |
| ---------------- | -------------------------------------------- | ---------------------------- |
| Про що           | справа: команда, розклад, навантаження       | людина: її стан і шлях       |
| Через що виникає | спільнота, домашня група, служіння, навчання | запис про попечительство     |
| Скільки          | скільки завгодно                             | кілька попечителів одночасно |
| Хто призначає    | адмін                                        | пастор або адмін             |

**Лідер команди не є автоматично попечителем** — для деяких служінь він ним є, для деяких ні.
**Лідер домашньої групи — завжди попечитель** її учасників: це сама природа домашки.

## Шари даних

Картка людини ділиться на чотири шари. Доступ дає не «картка цілком», а конкретний шар.

| Шар             | Що всередині                                                                                                                                 |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **Структурний** | імʼя, стать, спільноти, домашня група, служіння, навчання, сан, кого веде, членство й активність                                             |
| **Командний**   | + телефон, місто, дата народження, відвідуваність, навантаження                                                                              |
| **Обліковий**   | + пошта, адреса, індекс, район, область, домашній і робочий телефон, перший візит, хто привів, хрещення, член з, вибув                       |
| **Пасторський** | + нотатки, спілкування (дзвінки, зустрічі, консультації), кроки, хронологія, «потребує уваги», фолов-ап, сирітство, військова, сімейний стан |

Шари вкладені: кожен наступний містить попередній.

Межа між обліковим і пасторським — це межа між **даними реєстру** і **висновками про людину**.
Адреса, дата хрещення і хто привів — це те, що записують при оформленні; їх веде адміністратор,
і для цього не треба знати, що з людиною відбувається. Нотатки, кроки й сімейні обставини —
це вже пасторська робота.

Раніше шарів було три, і адреса з поштою лежали в пасторському. Через це адміністратор спільноти,
щоб виправити адресу, мусив мати доступ до нотаток — і саме тому роль адміна вийшла надто широкою.

## Хто який шар бачить

|                                            | Структурний | Командний | Обліковий | Пасторський |
| ------------------------------------------ | ----------- | --------- | --------- | ----------- |
| Будь-який лідер — по всій церкві           | ✓           | ✗         | ✗         | ✗           |
| Лідер команди — по своїх учасниках         | ✓           | ✓         | ✗         | ✗           |
| Адмін — у межах своїх рядків               | ✓           | ✓         | ✓         | ✗           |
| Попечитель — по своїх підопічних           | ✓           | ✓         | ✓         | ✓           |
| Лідер домашньої групи — по своїх учасниках | ✓           | ✓         | ✓         | ✓           |
| Роль `PASTOR` — по всіх, кого бачить       | ✓           | ✓         | ✓         | ✓           |
| Служитель конекту — по своїх нових людях   | ✓           | ✓         | ✓         | ✓           |

Тобто лідер прославлення D.Youth (я, наприклад) бачить структуру всієї церкви (імена й де хто
задіяний), командний шар своїх музикантів — і не бачить пасторського шару нікого, якщо він комусь
із них не призначений попечителем окремо.

**Конект — виняток з першого рядка**: служитель конекту не бачить структуру церкви взагалі.
Його світ — це борда нових людей своєї спільноти, і більше нічого.

**Шар рахується по кожній людині окремо, а не по користувачу.** В одному списку поруч стоять
картки підопічних (пасторський шар) і просто учасників команди (командний). Картка сама
повідомляє, що їй відкрито, щоб інтерфейс показував «вам це закрито», а не порожнє місце.

## Опіка

```
PersonCare: підопічний, попечитель, since, until, походження
```

Правила:

- **Кілька попечителів одночасно** — пастор і наставник можуть вести людину разом.
  Унікального «головного» не виділяємо, поки не зʼявиться потреба.
- **Попечитель бачить історію опіки**: попередніх попечителів і їхні пасторські записи.
  Без цього нова людина на служінні починає з чистого аркуша там, де потрібен контекст.
- **Призначає пастор або адмін.** Лідер не може взяти собі підопічного сам.
- **Походження запису** розрізняємо: `призначено` вручну, `домашня група` автоматично
  або `конект` — для служителя, який завів людину в базу. Це потрібно, щоб автоматичну опіку
  можна було закрити автоматично, не чіпаючи призначену.
- **Людина вийшла з домашньої групи** — автоматична опіка її лідера закривається (`until`),
  призначена вручну лишається.
- **Змінився лідер домашньої групи** — система пропонує перевести опіку над усіма учасниками,
  адмін підтверджує одним рішенням. Автоматично й мовчки це робити не можна: це масова зміна
  доступу до чутливого, вона має лишити слід.

Це заодно прибирає поле `connectedBy` — зараз це вільний текст із коментарем у схемі
«поки люди не можуть посилатися на людей». Тепер можуть.

## Ролі

| Роль         | Що може                                                                                  |
| ------------ | ---------------------------------------------------------------------------------------- |
| `SUPERADMIN` | усе в системі: користувачі й доступи, довідники (кроки, сани), чистка журналу, видалення |
| `ADMIN`      | веде реєстр: створює людей, переставляє в структурі церкви, призначає попечителів        |
| `LEADER`     | веде свої команди: командний шар учасників                                               |
| `CONNECT`    | заводить нових людей у свою спільноту і веде їх до передачі далі                         |
| `PASTOR`     | відкриває пасторський шар по всіх, кого користувач і так бачить                          |

**Ролі — це набір, а не одне значення.** Одна людина цілком може бути лідером домашньої групи
і водночас служити в конекті (Тоня). Якби роль була одна, довелося б заводити «лідер-конект» —
рівно те розмноження ролей, від якого ми відмовились у першому принципі.

**Глобальний адмін** — це `ADMIN` без обмеження області: бачить усю базу.
**Адмін спільноти** (Марта в молодіжці, Ронч на ранкових) — той самий `ADMIN` з областю
«спільнота D.Youth», «спільнота D.Church».

**Гілки церкви.** D.Youth і D.Church позначені як відгалуження (`is_branch`): у кожної своя
структура, свої адміни й свої цифри. Людина належить рівно до однієї гілки, і спільнота
обовʼязкова при заведенні картки — інакше людина не потрапляє в жодну гілку й видима лише
в загальному списку. Виняток — колишні члени: їх до гілок не приписуємо.

### Роль `PASTOR`

`PASTOR` — єдина роль, яка **не додає жодної людини** до видимих. Вона міняє глибину: те, що
користувач бачив командним чи обліковим шаром, він бачить пасторським.

Вона існує тому, що ми злили в `ADMIN` дві різні людини: **пастора**, якому пасторський шар
потрібен по суті служіння, і **адміністратора спільноти**, який веде структуру, а не душі.
Поки роль одна, вона мусить бути настільки широкою, як ширший із двох — і виходило, що адмін
без областей читає нотатки всієї церкви, бо колись комусь треба було виправити адресу.

Тепер правило одне для всіх, без винятків:

> **Пасторський шар відкриває опіка над конкретною людиною або роль `PASTOR`. Більше ніщо.**

`SUPERADMIN` з цього винятку теж прибрано. Адміністрування системи не є підставою читати
пасторські нотатки; кому треба — додає собі `PASTOR` явно, і це видно в журналі.

**Попечительство — не роль, а звʼязок.** Але людині, яка є попечителем і більше ніким,
тепер ставлять саме `PASTOR` без жодної області: вона бачить підопічних і нікого більше.
Раніше для цього ставили `LEADER` без областей, що читалось як «лідер, якому нічого не довірили».

## Що дає кожна роль окремо

Доступ рахується у два незалежні кроки: **кого видно** (рядки) і **що видно в картці** (шар).
Кожна роль вносить своє в обидва.

| Роль                     | Кого додає до видимих           | Який шар відкриває по них |
| ------------------------ | ------------------------------- | ------------------------- |
| `SUPERADMIN`             | усю базу (області ігноруються)  | обліковий                 |
| `ADMIN` без областей     | усю базу                        | обліковий                 |
| `ADMIN` з областями      | людей цих областей              | обліковий                 |
| `LEADER`                 | діючих учасників своїх областей | командний                 |
| `CONNECT`                | тих, кого привів сам            | пасторський (через опіку) |
| `PASTOR`                 | **нікого**                      | пасторський               |
| опіка — звʼязок, не роль | підопічних                      | пасторський               |

Три правила складання:

1. **Рядки складаються обʼєднанням.** Кілька ролей — бачиш суму того, що дає кожна.
2. **Шар береться найглибший**, який дає хоч одна роль у межах своїх рядків. Опіка діє точково:
   по підопічному пасторський шар відкритий навіть тоді, коли решта списку — командна.
3. **Без жодної ролі не видно нічого**, навіть за наявності підопічних. Порожній набір ролей —
   це вимкнений доступ, а не «лишилась хоч опіка».

Опіка працює тільки тоді, коли користувача **звʼязано з людиною** в базі: підопічні шукаються
по цьому звʼязку. Роль `PASTOR` звʼязку не потребує.

## Комбінації ролей

| Комбінація                      | Кого бачить                        | Що в картці                            | Хто це на практиці              |
| ------------------------------- | ---------------------------------- | -------------------------------------- | ------------------------------- |
| без ролей                       | нікого                             | —                                      | доступ вимкнено                 |
| `PASTOR`                        | підопічних                         | пасторський                            | наставник без інших функцій     |
| `LEADER`                        | свої області + підопічних          | командний; пасторський — по підопічних | лідер служіння                  |
| `LEADER` + `PASTOR`             | свої області + підопічних          | пасторський по всіх                    | лідер, який опікується командою |
| `CONNECT`                       | своїх нових + підопічних           | пасторський по своїх нових             | служитель конекту               |
| `CONNECT` + `LEADER`            | своїх нових + області + підопічних | по кожному свій шар                    | Тоня                            |
| `ADMIN` з областями             | людей областей + підопічних        | обліковий; пасторський — по підопічних | Марта, Ронч                     |
| `ADMIN` з областями + `PASTOR`  | людей областей + підопічних        | пасторський по всій області            | відповідальний за напрям        |
| `ADMIN` без областей            | усю базу                           | обліковий                              | адміністратор реєстру           |
| `ADMIN` без областей + `PASTOR` | усю базу                           | пасторський по всій церкві             | пастор                          |
| `SUPERADMIN`                    | усю базу                           | обліковий                              | технічний адміністратор         |
| `SUPERADMIN` + `PASTOR`         | усю базу                           | пасторський скрізь                     | максимум у системі; 0–1 людина  |
| `ADMIN` + `LEADER`              | те саме, що сам `ADMIN`            | обліковий                              | комбінація без сенсу            |

Про останній рядок: області — один спільний список користувача, а не окремий на кожну роль.
Тому `LEADER` поряд з `ADMIN` не додає нічого — ті самі області, вужчий шар.

`SUPERADMIN` ігнорує області: він завжди бачить усю базу, навіть якщо йому щось довірили явно.

### Приклад: відповідальний за всі домашні групи

Ролі `ADMIN` + `PASTOR`, області — кожна домашня група окремим записом. Він бачить усіх
учасників домашок пасторським шаром і може переставляти їх у структурі.

Але **«потребують уваги» в Огляді в нього буде порожнім**: цей блок рахується з опіки, а не
з областей — це робочий список конкретної людини, а не все, до чого є доступ, і `PASTOR` його
навмисно не розширює. Правильна відповідь тут не «розширити Огляд», а оформити йому опіку над
**лідерами домашок** — десяток записів. Це і є його справжній звʼязок: він опікується лідерами,
а не всіма двомастами учасниками.

### Чого роль `PASTOR` не міняє

- **Кого видно.** Жодної людини не додає — тільки глибину по тих, кого видно й так.
- **Права запису.** Переставляти людей у структурі церкви лишається `ADMIN`; довідники
  й видача доступів — `SUPERADMIN`.
- **Календар.** Видимість зібрань рахується з областей і ролі не стосується.
- **Огляд.** «Потребують уваги» і прострочені кроки лишаються на опіці.
- **Конект.** Борди роль не чіпає: там доступ і далі дає опіка служителя.

## Області відповідальності

Область — це явний запис «цьому користувачу довірено ось цю спільноту / домашню групу /
служіння / навчання», з рівнем **перегляд** або **ведення**.

- **Області задаються явно**, а не виводяться з того, хто де лідер. Лідерство в картці міняють
  часто й мимохідь; доступ до персональних даних так мінятися не повинен. В адмінці при цьому
  буде підказка: «Кірюха — лідер трансляції і домашньої групи Рудно. Додати ці області?» —
  в один клік.
- **Опіка — виняток**: вона дає доступ сама по собі, без окремого гранту. Це не суперечить
  правилу вище: призначення попечителя і є тим свідомим рішенням, яке ми вимагаємо.
- **Колишніх учасників лідер не бачить.** Людина вийшла зі служіння або перейшла в іншу
  домашню групу — вона зникає з поля зору попереднього лідера. Інакше доступ поступово
  розтікається на всю базу.
- Область дає доступ до людей, повʼязаних із нею **безпосередньо**. Область «спільнота»
  не відкриває автоматично людей усіх служінь усередині цієї спільноти.

## Конект

Дві команди конекту — на спільноту D.Youth і на спільноту D.Church. Їхня задача не губити
нових людей у телеграмі й нотатках телефону, а заводити їх у базу одразу після знайомства.

**Додавання за пів хвилини.** Обовʼязкових полів два: **імʼя** і **подія, на якій познайомились**.
Дата і служитель підтягуються самі. З цього одного екрана система створює:

- картку людини в спільноті команди;
- подію знайомства в її хронології;
- **опіку** служителя, який познайомився (походження `конект`);
- **крок «фолов-ап»** з ним же як відповідальним.

Тобто конект не «додає контакт», а відкриває людині шлях: одразу видно, хто за неї відповідає
і що має бути зроблене наступним.

**Борда.** Служитель бачить **тих, кого привів сам**: імʼя, подія й дата знайомства,
стан фолов-апу. Звідси людину можна **перекинути на колегу** — разом переходять
і фолов-ап, і ведення, тобто крок і опіка. Після передачі людина сходить з його борди
і зʼявляється на борді колеги.

Борди команди — спільного списку всіх нових людей спільноти — у служителя немає. Чужу нову
людину веде колега, і бачити її картку не входить у роботу служителя. Спільну борду спільноти
бачить адмін: йому потрібні саме ті, хто на ній засидівся.

**Межі доступу.** Служитель конекту не бачить ні структури церкви, ні інших людей — тільки тих,
кого привів. Це найвужчий доступ у системі, і таким він і має бути.

**Борда віддає не картку, а рядок.** Імʼя, телефон, подія знайомства, відповідальний і стан
фолов-апу — і нічого більше. Запит перелічує поля поіменно: вибірка «картка цілком» тягнула б
за собою нотатки й адресу, і шар протікав би повз усі перевірки.

**Скільки людина живе на борді.** Доти, доки фолов-ап не закрито й людину не передано далі —
в домашню групу або призначеному попечителю. Після передачі доступ конекту закривається.
Це принципово: інакше за рік команда конекту накопичить видимість пів церкви просто тому,
що колись їх зустріла. Якщо служитель хоче вести людину далі — його призначають попечителем
явно, і це вже інша підстава.

**Що потрібно доробити в моделі.** Подія знайомства матиме довідник заходів замість вільного
тексту. Відповідальний за крок зараз теж вільний текст; для передачі між служителями він має
стати посиланням на людину.

## Нотатки

Одного текстового поля на картку для цієї моделі замало: не видно, хто писав, і не можна
розділити шари. Нотатки стають списком записів з автором, датою і рівнем:

- **командний запис** — видимий лідерам команди й попечителям («пропустив три репетиції поспіль»);
- **пасторський запис** — лише попечителі, пастор, адміни.

## Флоу

**Нова людина приходить.** Служитель конекту заводить її з телефона за пів хвилини: імʼя й подія
знайомства. Людина одразу в спільноті, з подією в хронології, з опікою служителя й кроком
«фолов-ап». Якщо людину заводить адмін поза конектом — вона лишається без попечителя,
і її пасторський шар бачать тільки адміни й пастор.

**Фолов-ап.** Служитель або виконує його сам, або передає колезі по борді — разом із веденням.

**Передача далі.** Коли людину заводять у домашню групу або їй призначають попечителя,
вона сходить з борди, і доступ конекту закривається.

**Людину асайнять у команду.** Лідер отримує командний шар: бачить участь, навантаження, телефон.
Пасторського не отримує.

**Людину асайнять у домашню групу.** Лідер групи автоматично стає її попечителем і отримує
пасторський шар.

**Людині призначають попечителя.** Пастор або адмін створює запис. Попечитель бачить повну
картку й історію попередніх попечителів.

**Лідер команди бачить проблему, але не має пасторського доступу.** У картці він бачить рядок
«Попечителі: …» і кнопку «передати попечителю»: ставить позначку «потребує уваги» з коротким
коментарем, який лягає в пасторський шар, а не у відкриту картку. Попечитель бачить це у своєму
«Огляді». Так лідер не мовчить і не лізе, а система зʼєднує їх у правильному місці.

**Людина переходить в іншу домашню групу.** Опіка старого лідера закривається, нового —
відкривається; історія лишається видимою новому.

**Лідер хоче когось до себе.** Він бачить імʼя в структурі, але додати не може. Пропозиція:
кнопка «попросити додати» просто в структурі — створює заявку адміну, той підтверджує
в один клік. Це знімає заперечення щодо швидкості, не відкриваючи лідеру бази.

## Стартова сторінка

Лідеру не потрібен весь список людей церкви як головна сторінка. Замість нього — «Огляд»:

- **мої підопічні** — окремим блоком, бо попечитель може не бути лідером нічого;
- картки команд («Домашня група Єгора — 14 людей», «Прославлення D.Youth — 22»);
- хто потребує уваги (з підопічних) і сигнали, передані лідерами;
- прострочені кроки;
- дні народження цього тижня.

Навігація збирається з областей: немає жодної спільноти — пункт «Спільноти» не показуємо.
Розділ «Структура церкви» доступний усім лідерам, але це список без переходу в картки.

Для служителя конекту стартова сторінка — це **борда нових людей** його спільноти, і більше
нічого: ні списку людей, ні структури церкви.

Адміну на дашборді потрібні лічильники **«люди без попечителя»** і **«висить на борді довше
за N днів»** — і те, і те дірка, а не норма.

## Чому не «лідери бачать усіх, але без чутливих полів»

Був варіант: показувати лідерам усю базу без нотаток, телефону й адреси. Ми від нього відмовились,
і причина конкретна: якщо лідер може сам додати людину до своєї структури, то «без чутливих полів»
тримається рівно до того моменту, поки він не додасть людину собі, не прочитає все й не прибере назад.
Обмеження полів без обмеження асайну — це не захист, а незручність.

Саме тому рішення йдуть у парі: **структура з іменами видима всім лідерам**, але
**асайн — не в руках лідера**, а **пасторський шар — не в руках лідера команди**.

## Журнал як запобіжник

У системі вже є журнал операцій: кожна зміна картки записується з іменем виконавця,
старим і новим значенням. Якщо колись вирішимо дати лідерам право асайнити самим,
то «випадкове» додавання й видалення людини лишиться в журналі назавжди й буде видиме.
Це один із варіантів замість заборони — дозвіл під запис і періодичний перегляд.

## Що це означає для розробки

1. **Модель** — ролі як набір, звʼязок користувача з людиною, таблиця областей, таблиця опіки,
   нотатки як список записів з автором і рівнем, довідник заходів, відповідальний за крок
   як посилання на людину, зняття `connectedBy`.
2. **Бекенд** — видимість рахується як «область → командний шар» плюс «опіка → пасторський шар».
   Перевірка не одна, а дві, і поля картки віддаються за шаром. Тут головне — закрити «бічні двері»:
   списки для пікерів, лічильники на дашборді, масові дії за списком id, хронологія, події, кроки,
   експорт. Правило: новий ендпоїнт без явного шару не проходить ревʼю.
3. **Адмінка** — сторінка користувача: ролі (набір), області, рівень доступу; призначення
   попечителів; перенесення опіки при зміні лідера домашньої групи.
4. **Клієнт** — «Огляд» зі списком підопічних, розділ «Структура церкви», картка, що показує
   шари за доступом, кнопка сигналу попечителю.
5. **Конект** — екран швидкого додавання (імʼя + подія), борда служителя, передача людини
   колезі, довідник заходів.
6. **Перевірка** — сценарії на реальних даних: лідер служіння без опіки не дістає нотаток
   ні з картки, ні з хронології, ні експортом, ні прямим посиланням; служитель конекту
   не дістає нікого, крім своєї борди.

Обмеження живуть на сервері. Приховування кнопок у клієнті — косметика, і ніколи не заміняє перевірку.
